# TruckControl AI — Production Audit, Final Report

**Date:** 2026-08-19 · **Scope:** backend, web, Flutter driver app, database, deployment
**Method:** every claim below is backed by a test that runs against real PostgreSQL 16,
real Redis and real MinIO, or by a command whose output is quoted. Nothing is
marked PASS on inspection alone.

---

## 1. Overall status

**⚠️ READY AFTER FIXES**

All 10 original production blockers are closed and verified. Two things stand
between this and an unqualified "production ready", and neither is a code
defect — they are steps that can only be performed against the real deployment:

1. **No production environment exists yet to deploy to.** The Dockerfile,
   compose file, nginx config and CI pipeline are written and their logic is
   tested, but they have never run against production infrastructure. The
   container image is built in CI; it has not served real traffic.
2. **The 7th roadmap phase — the finance core (TZ §6) — is not built.** P&L
   formulas, fuel-norm comparison, maintenance and reports are still `[ ]` in
   `docs/ROADMAP.md`. The platform is secure and correct at what it currently
   does; it does not yet do everything the spec promises.

Neither is a reason to hold the fixes. The system went from "the driver app
cannot work at all and one tenant can write into another's data" to "every
blocking defect is closed with a regression test".

## 4. Defects found during the work

These were not in the original audit. Each was caught by a test written to
verify a fix, which is the point of writing them.

1. **The per-phone SMS limiter never fired.** `@nestjs/throttler`'s in-memory
   store treats a zero-length block as already expired and resets the counter,
   so the "1 code per minute per phone" rule was a no-op. Caught by
   `auth-security.e2e-spec.ts`.
2. **`MINIO_USE_SSL` was compared as a string.** The config schema coerces it to
   a boolean, so `=== 'true'` was always false — TLS to a remote object store
   would have been silently off, sending the access key in cleartext.
3. **The GPS index could not serve the live-map query.** `ORDER BY vehicle_id,
recorded_at DESC` cannot use an all-ascending index; `EXPLAIN` showed a
   sequential scan and sort over the whole table. Fixed by matching the index
   order, then by replacing `DISTINCT ON` (which PostgreSQL cannot skip-scan)
   with a lateral index probe per vehicle: 108 ms → 14 ms at 60k rows.
4. **`clientEventId` was globally unique.** Two tenants using the same offline
   client UUID collided across the tenant boundary: the scoped duplicate probe
   could not see the other company's row, so the insert failed with a 500
   instead of reporting a duplicate. Now unique per tenant.
5. **Health probes were rate limited.** A Kubernetes probe would eventually get
   429, read it as unhealthy and restart healthy pods. Now unthrottled and
   restricted at the edge instead.
6. **The readiness check hung the process.** A cached ioredis client whose
   server is unreachable retries forever and holds the event loop open, so the
   process would not shut down. Now a short-lived connection per probe.
7. **Mobile photo upload bypassed the injected HTTP client.** It built its own
   `MultipartRequest`, so it ignored every configured timeout and could not be
   tested. Moved into `ApiClient`.
8. **Sessions survived deactivation and password resets** for up to 30 days.
9. **`pg_dump` rejects Prisma's `?schema=` parameter** — a backup script written
   against `DATABASE_URL` fails at exactly the wrong moment. Both scripts now
   use plain libpq URLs and the restore script checks for it.

## 7. Build

Verified from a **git-only clone** (`git archive HEAD`), with no manual
preparation — this was the original failure mode:

```
pnpm install ............ PASS   (Prisma client generated by postinstall)
pnpm lint ............... PASS
pnpm typecheck .......... PASS   (3 packages)
pnpm format:check ....... PASS
pnpm test ............... PASS   (103 backend + 23 web)
pnpm build .............. PASS
prisma generate ......... PASS
prisma migrate deploy ... PASS   (all migrations applied to a clean database)
prisma db seed .......... PASS   (SUPERADMIN created, argon2id)
migrate diff ............ "This is an empty migration."  (no drift)
```

The original "14 failed suites on a clean clone" had two causes, both fixed at
the root rather than papered over with a documented pre-step: the Prisma client
was never generated (now a `postinstall` hook), and `shared` resolved to a
`dist/` that did not exist yet (now resolved from source via tsconfig `paths`).

Bundle: **497 kB → 308 kB** initial (152 kB → 100 kB gzipped); Leaflet is a
separate 154 kB chunk fetched only by the map page.

## 12. Verdict

**⚠️ READY AFTER FIXES**

Every blocker in the original audit is closed, and each fix carries a regression
test that runs against real infrastructure rather than a mock. On the code, the
system is production-grade.

It is not yet **PRODUCTION READY** in the full sense, for two honest reasons:
the deployment configuration has never run against real production
infrastructure, and the finance core the specification calls for (TZ §6) has not
been built. Calling it ready today would be claiming something this session did
not verify.

**Recommended next steps, in order:**

1. Deploy to staging with `docker-compose.prod.yml` and run one restore drill.
2. Build the finance module (roadmap phase 7) — it is the reason the product exists.
3. Run a pilot with one real company before opening to the other.
